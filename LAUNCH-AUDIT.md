# Peakr Launch Gap Audit

_Generated 2026-06-10 by a 33-agent audit workflow: 7 dimension auditors + adversarial verification of every critical/high finding + completeness critic. All 25 critical/high findings were independently confirmed against the code (0 refuted)._

**Totals:** 5 critical · 18 high · 30 medium · 14 low

## Checklist by severity

### CRITICAL (5)

- [ ] **POST /api/analyze-hook is completely unauthenticated and triggers the paid analysis pipeline** — `src/app/api/analyze-hook/route.ts:4` _(AI Features)_
  - The analyze-hook route never calls auth() (it doesn't even import it), and middleware only matches '/dashboard/:path*', so this API is fully public on Vercel. Any anonymous caller can enumerate sequential integer post_ids and flip every post in the database to hook_analysis='{"status": "pending"}'. The Mac Mini daemon's fast path (scraper/daemon.py:203-218) then processes each pending post — full video download via yt-dlp, Whisper transcription, and a Claude call through OpenClaw — one per loop iteration. Critically, manually-queued pending posts bypass BOTH cost controls: the viral_score>=1.5 threshold and the MAX_PER_ACCOUNT=20 cap (those are only enforced in run_analysis_pass in scraper/analyze.py:111-138; the fast path calls analyze_post directly). Because the fast path 'continue's after each post, a large queued backlog also starves all scheduled scraping indefinitely.
  - **Fix:** Add the same auth() guard used by every other route, verify the post belongs to a profile the requesting user tracks (join user_tracked_profiles), and add a simple per-user daily cap on manual analysis requests. Keep the fast path subject to MAX_PER_ACCOUNT.

- [ ] **Daemon livelocks in a zero-sleep infinite retry loop when a queued post fails analysis** — `scraper/daemon.py:203` _(AI Features)_
  - When analyze_post() fails, the '{"status": "pending"}' flag is never cleared (only save_hook_analysis on success sets analyzed_at). The daemon fast path selects pending posts ORDER BY p.id DESC LIMIT 1 (scraper/db.py:446-459), so the SAME failing post is re-selected every iteration, and the `continue` at daemon.py:216 skips the `time.sleep(5)` at line 318. analyze_post fails deterministically for posts with no post_url or duration_seconds > 300 (scraper/analyze.py:38-44), and queue_top_posts_for_analysis / the track route queue the top-5 posts by viral score with NO duration or is_video filter. So the moment any user tracks an account whose top post is a 6-minute video, the daemon spins forever: hammering RDS at full speed, never reaching scheduled scrapes, overnight analysis, or stale-profile refresh (lines 220-316 become unreachable). If the failure is at the LLM step instead (OpenClaw down, malformed JSON), each retry also re-downloads the full video via yt-dlp and re-calls the LLM with no backoff and no attempt cap — burning bandwidth, Claude Max quota, and risking IP bans from TikTok/Instagram. Meanwhile the web UI shows 'queued' forever: InsightsPanel.tsx sets status 'queued' with no polling and the backend never records failure.
  - **Fix:** On failure, write a terminal marker (e.g. hook_analysis = '{"status":"failed","attempts":N}') and exclude failed/over-attempted posts from get_unanalyzed_viral_posts; cap retries at 2-3; sleep before `continue`; filter is_video=TRUE AND duration<=300 when queueing top posts. Surface 'failed' to the UI instead of perpetual 'queued'.

- [ ] **image-proxy and video-url are unauthenticated SSRF proxies that fetch arbitrary URLs** — `src/app/api/image-proxy/route.ts:10` _(API Authorization)_
  - src/app/api/image-proxy/route.ts takes a caller-supplied url query param and does fetch(url) server-side with no validation of scheme, host, or IP, returning the response body. src/app/api/video-url/route.ts does the same and passes the url to yt-dlp via execFile. Neither route checks the session. On Vercel this lets an anonymous attacker make the server issue requests to arbitrary destinations (internal metadata endpoints, internal-only hosts reachable from the function, redirect targets) and read back the bytes (image-proxy returns the raw body; video-url returns the resolved URL/errors). proxyImg() in src/lib/format.ts only ever builds image-proxy URLs for instagram/cdninstagram hosts, but the route enforces no such restriction.
  - **Fix:** Validate the URL before fetching: require https:, resolve and reject private/loopback/link-local IP ranges (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, ::1, fc00::/7), and enforce a host allowlist (instagram/cdninstagram for image-proxy; tiktok/instagram for video-url). Disable or re-validate redirects. Add auth() and cap yt-dlp concurrency.

- [ ] **RDS database is publicly accessible with port 5432 open to the entire internet** — `terraform/main.tf:32` _(Infrastructure & Ops)_
  - The Terraform config creates the RDS instance with publicly_accessible = true and a security group that allows PostgreSQL ingress from 0.0.0.0/0. The comment in the file acknowledges this is to accommodate Vercel's dynamic IPs. This exposes the master credential to internet-wide brute forcing, and the Node client connects with ssl rejectUnauthorized: false (src/lib/db.ts:10-12), so the TLS certificate is never validated. The master password stored in terraform.tfstate is a short dictionary-word password, compounding the brute-force exposure.
  - **Fix:** Before launch, at minimum rotate the master password to a long random value and enforce SSL cert validation (download the RDS CA bundle and set ssl: { ca }). Better: restrict ingress to the Mac Mini's static IP plus a Vercel-compatible path (Vercel Secure Compute, an IP-allowlisted PgBouncer/proxy, or move to a pooled provider like Neon/Supabase/RDS Proxy). Keep publicly_accessible only if a hardened password + cert validation are in place.

- [ ] **One permanently-failing analysis job starves the entire daemon (infinite 5s retry loop, no error marking)** — `scraper/daemon.py:203` _(Scraper Pipeline)_
  - The daemon's fast-path analysis (daemon.py lines 203-218) fetches the newest pending post every loop iteration and calls analyze_post(). When analysis fails — OpenClaw at 127.0.0.1:18789 down, deleted/region-locked video, invalid JSON from the model — analyze_post() returns False without writing anything to the post row (analyzed_at stays NULL, hook_analysis stays '{"status": "pending"}'). get_unanalyzed_viral_posts orders priority-1 posts by id DESC with LIMIT 1, so the exact same post is re-selected every 5 seconds, forever. Each attempt can take minutes (yt-dlp 120s timeout, whisper 300s, OpenClaw 120s). Worse, the `continue` after the analysis attempt means the scheduled seed scrapes, overnight analysis, daily maintenance, AND the stale-profile refresh loop below it never execute while a stuck pending post exists. If OpenClaw is down, every queued post fails and the entire refresh pipeline halts — tracked profiles go stale indefinitely while the daemon burns CPU re-downloading the same video.
  - **Fix:** On analysis failure, write a failure marker to the post (e.g. hook_analysis = '{"status": "failed", "attempts": N}') and exclude failed posts (or posts with attempts >= 3) from get_unanalyzed_viral_posts. Remove the unconditional `continue` so scheduled jobs and stale refresh still run, or move the fast-path behind a per-post cooldown.

### HIGH (18)

- [ ] **No rate limiting, quota, or debounce on any LLM endpoint — authenticated users can spam unbounded DeepSeek calls** — `src/app/api/playbook/regenerate/route.ts:146` _(AI Features)_
  - All five DeepSeek-backed routes (playbook/generate-hooks, playbook/regenerate, hooks/remix, creator-profile/questions, creator-profile/suggestions) fire a fresh DeepSeek API call on every request with no per-user quota, no cooldown, no idempotency, and no concurrency guard. A grep for rate-limit/upstash/debounce across src/app/api returns nothing. Three of the five (generate-hooks, regenerate, remix) also send no max_tokens, relying on provider defaults. A single user holding down the regenerate button — or a script with one session cookie — produces unbounded spend on the operator's DeepSeek account and can exhaust provider rate limits, breaking AI features for all users. Similarly, /api/track lets a user track unlimited accounts, each enqueueing 5 video downloads + Whisper + Claude analyses on the Mac Mini with no cap on tracked accounts per user.
  - **Fix:** Add a lightweight per-user rate limit (e.g. a generations_log table checked per request, or Upstash Ratelimit) — e.g. 10 generations/hour — plus max_tokens on every DeepSeek call, and a cap on tracked profiles per user. Client-side, disable the button while a request is in flight.

- [ ] **saved-posts endpoints have no auth and operate on a global, non-user-scoped table** — `src/app/api/saved/[id]/route.ts:11` _(API Authorization)_
  - src/app/api/saved/route.ts (GET/POST/DELETE) and src/app/api/saved/[id]/route.ts (DELETE) perform NO auth() check, and the underlying saved_posts table (src/lib/db.ts:89-95) has no user_id column. So (1) any unauthenticated caller can GET every saved post including notes; (2) any caller can DELETE another user's saved post by iterating the integer id (saved/[id]/route.ts:11 `DELETE FROM saved_posts WHERE id = $1`, no ownership predicate) or by post_id; (3) because saved_posts has UNIQUE(post_id), a POST by user A overwrites user B's folder/notes for the same post. The newer saved/import route is auth-aware and the saved page uses it, but these bare handlers are still deployed and reachable.
  - **Fix:** Retire these legacy routes (the app already uses user-scoped saved_hooks/user_saved_patterns) or add auth() plus a user_id column to saved_posts and scope all reads/writes/deletes by user_id = session.user.id.

- [ ] **/api/export dumps the entire posts + profiles dataset with no authentication** — `src/app/api/export/route.ts:14` _(API Authorization)_
  - src/app/api/export/route.ts has no auth() check and runs SELECT ... FROM posts p JOIN profiles pr ... with no WHERE clause and no user scoping, returning every post and profile as CSV or JSON. Any anonymous visitor hitting GET /api/export?format=csv exfiltrates the full scraped corpus (all users' tracked accounts, descriptions, view/like/engagement metrics, post URLs). The analytics page opens this URL behind the dashboard, but the route is publicly reachable since middleware only covers /dashboard page routes, not /api.
  - **Fix:** Add auth() and scope the export to the caller's tracked profiles via JOIN user_tracked_profiles utp ON utp.profile_id = pr.id AND utp.user_id = $1, mirroring tracked-posts/analytics.

- [ ] **No rate limiting on expensive unauthenticated and AI endpoints** — `src/middleware.ts:20` _(API Authorization)_
  - There is no rate-limiting middleware or library anywhere (grep for rate-limit/upstash/@vercel/kv returns nothing; src/middleware.ts only redirects unauthenticated users from /dashboard pages and does not touch /api). Several endpoints do expensive work per request: video-url spawns a yt-dlp subprocess; search-accounts and saved/import make live outbound scrapes to instagram.com/tiktok.com; analyze-hook (no auth) flips posts to pending-analysis feeding the AI pipeline; and the auth'd AI routes (playbook/generate-hooks, playbook/regenerate, hooks/remix, creator-profile/questions, creator-profile/suggestions) each make a paid DeepSeek call per request. An attacker can loop the unauthenticated ones to burn the operator's IP reputation (Instagram/TikTok blocking), exhaust Vercel function time, and run up the DeepSeek bill once they have a free account. The credentials login path (src/lib/auth.ts authorize) is also unthrottled, enabling password brute-force.
  - **Fix:** Add a rate limiter (Upstash/@vercel/kv ratelimit or Vercel Firewall) keyed by IP for unauthenticated routes and by user id for AI routes. Throttle authorize() (per-email + per-IP) to stop brute force. Cap concurrent yt-dlp subprocesses.

- [ ] **No rate limiting on login or signup — brute force, credential stuffing, and signup spam are unthrottled** — `src/lib/auth.ts:17` _(Auth & Sessions)_
  - Neither the credentials authorize() path (src/lib/auth.ts:17) nor the signup route (src/app/api/auth/signup/route.ts:5) applies any rate limiting, lockout, or CAPTCHA. An attacker can hammer /api/auth/callback/credentials with unlimited password guesses against a known email, run credential-stuffing lists, or mass-create accounts via /api/auth/signup (each signup runs a bcrypt cost-12 hash, which also makes the endpoint a cheap CPU-exhaustion / cost-amplification vector on Vercel). There is no IP throttle, no per-account attempt counter, and JWT sessions mean no server-side login auditing exists either.
  - **Fix:** Add rate limiting before launch: e.g. Upstash/Vercel KV-backed limiter (or Vercel Firewall rules) on /api/auth/callback/credentials and /api/auth/signup keyed by IP and by email, with exponential backoff and a hard lockout threshold. Consider a CAPTCHA on signup. This is the single most important hardening step for a public launch.

- [ ] **Several data API routes have no auth() check (middleware only guards /dashboard)** — `src/app/api/export/route.ts:8` _(Auth & Sessions)_
  - Route protection is enforced two ways: middleware.ts only matches '/dashboard/:path*', and individual API routes must each call auth(). Many do, but several read or mutate data with no session check at all, so they are reachable anonymously. /api/export (GET) dumps EVERY post joined to EVERY profile (username, follower counts, descriptions, viral_score, post_url) as CSV with zero auth — a full dataset exfiltration endpoint. /api/saved (GET/POST/DELETE) and /api/saved/[id] (DELETE) operate on a global saved_posts table that has no user_id column, so any anonymous caller can read and delete the shared saved set. /api/analyze-hook and /api/video-url are also unauthenticated and trigger work (DB writes / yt-dlp subprocess) on arbitrary input. The middleware comment in CLAUDE.md implies dashboard pages are protected, but the API surface behind them is not uniformly gated.
  - **Fix:** Add an explicit `const session = await auth(); if (!session?.user?.id) return 401` to every API route that reads or writes app data — start with /api/export, /api/saved, /api/saved/[id], /api/analyze-hook, /api/video-url, /api/image-proxy. Better still, extend the middleware matcher to cover /api (excluding /api/auth) as defense-in-depth so a future unauthed route does not silently leak. Separately, saved_posts is global with no user_id; scope it per user.

- [ ] **No password reset or account recovery flow exists — and no email-sending capability anywhere in the stack** — `src/app/api/auth/change-password/route.ts:6` _(Missed-by-audit sweep)_
  - The only auth endpoints are signup, change-password (requires an active session), and the NextAuth handler. There is no forgot-password route, no reset-token table, and the login page has no 'forgot password' link. A grep across src/ and package.json finds no mail library (resend, nodemailer, sendgrid, SES, postmark) — the app cannot send any email. A credentials user who forgets their password is permanently locked out, and the operator has no in-app tooling to reset it (only manual SQL against RDS). This will generate support requests within days of launch. The same absence of email infrastructure also means signup performs no email verification, so the email-enumeration and spam-signup findings cannot be mitigated by verification later without building this from scratch.
  - **Fix:** Add a forgot-password flow before launch: a password_reset_tokens table, a request endpoint that emails a single-use expiring token (Resend is the lightest lift on Vercel), and a reset page. Reuse the same email plumbing for signup verification later.

- [ ] **Node schema init is broken on a fresh database: ALTER TABLE creator_profiles runs before the table is created, and the failure is swallowed** — `src/lib/db.ts:114` _(Database & Data Integrity)_
  - In src/lib/db.ts, initSchema() runs an ALTER batch (lines 107-117) that includes `ALTER TABLE creator_profiles ADD COLUMN IF NOT EXISTS content_topics TEXT`, but creator_profiles is only created later, at line 154 (the 'Phase 3' block). On a fresh database where Node connects first (e.g., new Vercel env, staging, disaster recovery), the ALTER batch throws 42P01 (relation does not exist). Because pg executes a multi-statement query in one implicit transaction, the entire ALTER batch rolls back (so posts.keyframe_base64/audio_name/audio_author and profiles.primary_niche are also never added), initSchema() aborts, and every table defined after that point — video_url_cache, seed_creators, daily_top_hooks, creator_profiles, saved_hooks, playbook_sections, user_tracked_profiles, user_hooks, user_hook_examples, hook_patterns, hook_pattern_posts, user_saved_patterns, hook_collections, hook_collection_patterns, notifications — is never created. The error is swallowed by `initSchema().catch(console.error)` in getPool() (line 16), so the app boots normally and then 500s on /api/track (user_tracked_profiles missing), /api/hook-lab (seed_creators missing), etc. The deployment only works today because the Python side (scraper/db.py SCHEMA, which creates creator_profiles in its first pass) initialized the DB first. Python-first ordering works; Node-first does not — there is no working Node-only bootstrap path.
  - **Fix:** Move the ALTER block after all CREATE TABLE statements (or simply move the `ALTER TABLE creator_profiles` line below the Phase 3 block). Better: collapse initSchema into one ordered list of statements executed sequentially, and make schema-init failures loud (fail the request or at minimum retry on next call instead of caching a half-initialized state). Verify by pointing the web app at an empty database and exercising /api/track and /api/hook-lab.

- [ ] **saved_posts has no user_id column and its API routes have no auth — saves are global across all users and publicly writable** — `src/app/api/saved/route.ts:46` _(Database & Data Integrity)_
  - The saved_posts table (src/lib/db.ts:89-95 and scraper/db.py:76-82) has only `post_id INTEGER UNIQUE REFERENCES posts(id)` — no user_id. Every user therefore shares one global set of saved posts: user A saving or unsaving a post changes what user B sees (hook-lab and explore routes compute `(sp.id IS NOT NULL) AS is_saved` from this global table). Worse, src/app/api/saved/route.ts performs GET/POST/DELETE with no auth() check at all, and src/middleware.ts only matches `/dashboard/:path*`, so any unauthenticated client can list, create, or delete saved posts (`DELETE FROM saved_posts WHERE post_id = $1` with no ownership filter). The UNIQUE(post_id) constraint plus `ON CONFLICT (post_id) DO UPDATE` means two users can never save the same post independently — the second save overwrites the first user's folder/notes.
  - **Fix:** If saved_posts is legacy (replaced by user_saved_patterns/'My Hooks' per recent commits), remove the /api/saved* routes and the is_saved join before launch. If it must stay, add a user_id column with UNIQUE(user_id, post_id), backfill, add auth() checks to all three handlers, and scope every query by user_id.

- [ ] **32-bit INTEGER columns overflow for top creators: profiles.total_likes and posts.views** — `src/lib/db.ts:48` _(Database & Data Integrity)_
  - Both schemas define `total_likes INTEGER` on profiles and `views INTEGER` on posts (src/lib/db.ts:48,63; scraper/db.py:35,50). PostgreSQL INTEGER caps at 2,147,483,647. The TikTok scraper writes heartCount directly (scraper/tiktok.py:178 `result['total_likes'] = stats.get('heartCount', ...)`, written via update_profile at tiktok.py:126-132). Major creators — exactly the accounts users will track at launch — have heartCounts far above 2.1B (Khaby Lame ~2.5B, Charli D'Amelio ~11B). psycopg2 will raise 'integer out of range', the daemon's scrape_one() catches and logs the exception, and that profile silently never gets scraped — the user just sees a tracked account with no data, forever. Individual posts above 2.1B views are rarer but exist on TikTok, and posts.views has the same cap.
  - **Fix:** Run `ALTER TABLE profiles ALTER COLUMN total_likes TYPE BIGINT;` and `ALTER TABLE posts ALTER COLUMN views TYPE BIGINT;` (followers/likes/comments can stay INTEGER but BIGINT is cheap insurance), and update both schema files' CREATE statements to match. JS reads BIGINT back as string via pg, so coerce with Number() or set a pg type parser where these fields feed arithmetic.

- [ ] **No payment/billing integration exists; pricing UI and FAQ promise a checkout that is not in the codebase** — `src/components/Pricing.tsx:109` _(Frontend & UX)_
  - The landing page sells two paid plans ($12 first month / $120 annual) and the FAQ explicitly states 'The monthly plan includes 50% off for month 1 at checkout. You can cancel your subscription at any time.' But there is no checkout anywhere: both Pricing CTAs link to /signup, grep finds no Stripe/Paddle/LemonSqueezy in package.json or src/, the dashboard sidebar 'Upgrade' button has no onClick handler and no href (a dead button rendered on every dashboard page), and the Account page hardcodes 'Current Plan: Monthly' with a hardcoded trackLimit of 15 for every user. The 15/50-account limits advertised in pricing are also not enforced — POST /api/track (src/app/api/track/route.ts) inserts with no count check. At launch, every user gets everything free while the marketing copy makes billing promises the product cannot keep.
  - **Fix:** Decide the launch posture explicitly: either wire a real checkout (Stripe Checkout is a day of work) and enforce plan limits in /api/track, or strip the pricing/FAQ billing claims and the dead Upgrade button and launch as a free beta. Shipping copy that references a nonexistent checkout invites chargeback/legal complaints and erodes trust immediately.

- [ ] **No usable backup/recovery posture for the production database** — `terraform/main.tf:63` _(Infrastructure & Ops)_
  - All user data (users, profiles, posts, saved hooks, playbooks) lives in one db.t4g.micro with backup_retention_period = 1 (one day of automated backups), skip_final_snapshot = true (terraform destroy deletes the DB with no snapshot), and no deletion_protection. A bad migration noticed two days later, an accidental `terraform destroy`, or instance loss means unrecoverable data loss for every customer.
  - **Fix:** Set backup_retention_period to 7+, deletion_protection = true, skip_final_snapshot = false with a final_snapshot_identifier, and consider copy_tags_to_snapshot. This is a 4-line Terraform change and should land before real users sign up.

- [ ] **Terms of Service and Privacy Policy pages do not exist — blocks TikTok OAuth review** — `src/app/login/page.tsx:179` _(Infrastructure & Ops)_
  - The login page tells users 'By continuing, you agree to our Terms of Service and Privacy Policy' but no such pages exist anywhere in src/app (only page.tsx, login, signup, dashboard, api). The landing footer renders 'Privacy' and 'Terms' as plain non-link <span> elements. TikTok's developer app review requires live Terms of Service and Privacy Policy URLs, so the TikTok OAuth provider — one of the two sign-in methods — cannot pass production app review without them. A privacy policy is also legally required (CCPA/GDPR) for an app collecting emails and OAuth identities.
  - **Fix:** Add /terms and /privacy routes with real content before launch, link them from the login page and footer, and register those URLs in the TikTok developer portal app submission.

- [ ] **Core scraping pipeline has zero monitoring: no health endpoint, no daemon heartbeat, no alerting** — `scraper/daemon.py:37` _(Infrastructure & Ops)_
  - The product's core loop (POST /api/track inserts a row; the Mac Mini daemon polls and scrapes) silently breaks if the daemon dies, the Mac Mini reboots, the SOCKS5 proxy drops, or Instagram/TikTok block the scrapers. There are 37 API routes but no /api/health or worker-status endpoint, the daemon writes only a PID file (PID_FILE = /tmp/peakr-daemon.pid) with no heartbeat row or external check-in, and grepping the scraper for alert/heartbeat/webhook/slack/telegram finds nothing. New users who track an account would see a profile that never populates, and the operator would have no signal.
  - **Fix:** Minimum viable: have the daemon write a heartbeat timestamp to a DB table each loop, add GET /api/health that reports DB connectivity and heartbeat staleness, and point a free uptime checker (UptimeRobot/Healthchecks.io) at it — plus a Healthchecks.io ping directly from the daemon loop so a dead Mac Mini pages you.

- [ ] **Daemon dies on any transient DB error; no supervisor config or single-instance lock exists in the repo** — `scraper/daemon.py:185` _(Scraper Pipeline)_
  - pop_scrape_queue() (daemon.py:185) and get_active_profiles() (daemon.py:265) are called directly in the main loop with no try/except. Any psycopg2.OperationalError — RDS failover, network blip on the Mac Mini, connection limit — propagates out of the while loop (the surrounding try has only a finally, no except) and the daemon exits. The repo contains no launchd plist, supervisor config, or start script (only scripts/migrate-hooks.ts), so recovery depends entirely on an out-of-repo cron job. Additionally, the PID file is written but never checked, so nothing prevents two daemon instances from running concurrently after a restart — and pop_scrape_queue's UPDATE-with-subselect (db.py:533-539) has no FOR UPDATE SKIP LOCKED, so two instances can double-claim the same queue row.
  - **Fix:** Wrap the main loop body in try/except with backoff on DB errors so transient outages don't kill the process. Commit a launchd plist with KeepAlive=true (macOS-native supervision) to the repo so restart behavior is reproducible. Check the PID file (os.kill(pid, 0)) on startup and exit if another instance is alive, and add FOR UPDATE SKIP LOCKED to the pop_scrape_queue subselect.

- [ ] **Instagram session expiry is a silent, permanent failure requiring manual interactive login on the Mac Mini** — `scraper/instagram.py:139` _(Scraper Pipeline)_
  - When the saved cookies in data/cookies/instagram.json expire or are invalidated, _has_valid_session() returns False, scrape_profile() returns None, and scrape_and_store() returns False. Nothing distinguishes 'session dead' from a transient error: last_scraped_at is never updated, so the daemon re-attempts every IG profile every refresh cycle — each attempt launching a full Chromium browser, hitting instagram.com while logged-out, failing, and sleeping 60-75s — indefinitely. There is no failure counter, no backoff, no alert. The only fix is a human running `python3 -m scraper.instagram --login` (which uses input() and a visible browser) on the Mac Mini. Until then, every user-tracked IG profile silently stops updating. Note also the cookie file lives in gitignored data/, so a fresh clone/redeploy starts with no session at all.
  - **Fix:** Detect the invalid-session state distinctly (e.g. write a 'session_invalid' flag or a scrape_log status='auth_failed'), stop attempting IG scrapes while it is set, and alert the operator (email/Slack/push — even a daily digest). Track consecutive failures per profile and back off exponentially. Document a cookie-refresh runbook.

- [ ] **Instagram scraping uses plain headless Chromium with no proxy — contradicts the documented Camoufox+WARP strategy and risks banning the session and home IP** — `scraper/instagram.py:41` _(Scraper Pipeline)_
  - docs/SCRAPING-PLAN.md and CLAUDE.md both state Instagram scraping goes through Camoufox with the WARP SOCKS5 proxy. The actual BrowserSession launches stock Playwright Chromium headless with a spoofed UA string and never passes a proxy — the PROXY constant is only used by login_interactive(). So the burner account logs in via Camoufox+WARP (Cloudflare IP, Firefox fingerprint) and then scrapes from the Mac Mini's raw IP with a headless-Chromium fingerprint (navigator.webdriver=true, UA/engine mismatch). That IP/fingerprint discontinuity on a logged-in session is exactly what gets accounts flagged, and it exposes the operator's home IP to Instagram on every scrape. The class docstring even claims a Camoufox fallback that is not implemented.
  - **Fix:** Pass proxy={'server': 'socks5://127.0.0.1:1080'} to the browser launch (and refuse to scrape, with an alert, if the proxy is down), or actually use Camoufox as the docstring claims so login and scraping share fingerprint and IP.

- [ ] **Zero error visibility: scrape_log is write-only, no alerting, and users never see scrape status or data freshness** — `scraper/db.py:384` _(Scraper Pipeline)_
  - scrape_log faithfully records successes and errors, but nothing reads it: no API route, no dashboard widget, no health check. There is no daemon heartbeat, so if the daemon dies or the IG session expires, neither the operator nor users get any signal. The frontend never displays last_scraped_at (it exists only in the TypeScript type definition) or any 'scraping in progress / failed' state — a user who tracks a profile while the pipeline is broken sees a profile card with zero posts indefinitely, with no explanation and no way to tell stale data from fresh. For a product whose core promise is fresh viral-content data, silent staleness is a launch-level gap.
  - **Fix:** Minimum for launch: (1) daemon writes a heartbeat row every loop; (2) a /api/health or admin view that surfaces last heartbeat + recent scrape_log error rate; (3) show 'last updated X hours ago' (and 'scrape queued/failed') on profile cards so users can distinguish stale data; (4) a simple operator alert (email via Resend, which the operator already uses elsewhere) when heartbeat is stale >15 min or error rate spikes.

- [ ] **Regenerate persists unvalidated LLM output — wrong-shaped JSON silently nulls out an existing playbook section** — `src/app/api/playbook/regenerate/route.ts:171` _(AI Features)_

## Dimension health summaries

### Auth & Sessions

Authentication is built on Auth.js v5 (JWT sessions) with two providers — TikTok OAuth and email/password credentials — and the core mechanics are mostly sound: bcrypt cost 12, server-side password verification, current-password check on change-password, trustHost set, secureCookie correctly toggled in middleware for Vercel HTTPS, and env secrets properly gitignored (nothing committed). The feared account-takeover-via-email-collision vector is not present, because the TikTok signIn/jwt callbacks never store an email, so OAuth and credentials rows can never collide on the email unique key. However there are several launch-blocking gaps: the credentials authorize() function logs plaintext user emails to server (Vercel) logs on every failed and successful login; there is zero rate limiting on signup or login, leaving brute-force, credential-stuffing, and signup-spam wide open; the signup endpoint leaks account existence via a distinct 409 message (email enumeration); the password policy is length-only; route protection relies entirely on per-route auth() calls with the middleware covering only /dashboard, and several data API routes ship with no auth check at all (notably /api/export dumps the entire posts+profiles dataset and /api/saved exposes a global, user-unscoped saved bucket to anonymous callers). These should be fixed before launch.

### API Authorization

Peakr's API surface is a mixed bag. The team got the hard parts mostly right: every SQL query I read is parameterized (including dynamic filter construction in hook-lab/user-hooks via indexed $N placeholders), and ORDER BY/sort values come from whitelisted switch statements rather than user strings, so there is no SQL injection. Most user-owned resources (playbook, collections, notifications, saved-hooks, user-hooks, creator-profile, analytics, tracked-posts, track) correctly call auth() and scope every query by the session user id. However, a cluster of legacy/global endpoints ship with NO authentication and operate on a shared, non-user-scoped saved_posts table; there is an unauthenticated full-data export; and two classic SSRF proxies (image-proxy, video-url) fetch arbitrary caller-supplied URLs server-side. The Next.js middleware only guards /dashboard page routes — it does NOT cover /api/*, so each API route owns its auth and several don't do it. There is zero rate limiting anywhere, and several unauthenticated endpoints trigger expensive work (yt-dlp subprocess, external scraping, AI queueing). These are the launch-blockers; the rest of the surface is solid.

### Database & Data Integrity

The two schema definitions (src/lib/db.ts and scraper/db.py) are column-compatible today, but only because both sides' ad-hoc ALTER/migration blocks happen to run on the existing production database. The sync mechanism itself is fragile and the Node bootstrap is actually broken: db.ts runs an ALTER against creator_profiles before that table is created, so a fresh database initialized by the web app alone fails partway through and silently leaves ~15 tables missing (errors are swallowed by .catch(console.error)). There is no versioned migration system — everything is CREATE IF NOT EXISTS plus scattered ALTERs, several indexes exist only on the Node side, and full DDL re-runs on every Vercel cold start. Beyond sync, there are concrete launch risks: profiles.total_likes/posts.views are 32-bit INTEGERs that overflow for exactly the mega-creators users will track; the legacy saved_posts table has no user_id and its API routes have no auth, so saves are global and publicly writable; and the pg pool is sized at max:10 per serverless instance, which can exhaust a small RDS instance under modest concurrency. Fixable in a day or two, but the bootstrap bug, the integer overflow, and the unscoped saved_posts table should be fixed before launch.

### Scraper Pipeline

The scraper pipeline works on the happy path but has essentially no failure-recovery design, and several of its failure modes are silent and self-reinforcing. The most dangerous: a single permanently-failing analysis job starves the entire daemon loop (stale-profile refresh and all nightly jobs stop running); an unhandled DB hiccup kills the daemon outright with no supervisor config or single-instance lock anywhere in the repo; a daemon crash mid-scrape leaves a scrape_queue row stuck 'in_progress' forever, which permanently blocks the affected profile from ever being re-queued by the Track button; and Instagram session expiry turns every IG scrape into an endless silent retry loop that only a human running an interactive login on the Mac Mini can fix. Anti-detection is also weaker than documented: Instagram scraping uses plain headless Chromium with no proxy (only login goes through Camoufox+WARP), TikTok silently falls back to the raw IP when wireproxy is down (and wireproxy lives in /tmp, wiped on reboot), and yt-dlp subprocesses are never proxied. Finally, there is zero error visibility: scrape_log is written but never read, the frontend never shows last_scraped_at or scrape status, and nothing alerts the operator when scraping silently breaks. These should be addressed before launch; the happy-path scraping logic itself (parsing, upserts, viral scoring) looks solid.

### Frontend & UX

The dashboard frontend is genuinely feature-rich and mostly polished: every page has loading spinners and designed empty states, mobile gets a bottom nav plus hamburger sidebar, and the Hook Lab / My Hooks / Playbook flows are coherent with good inline feedback (copy buttons, optimistic collection toggles, status banners on the Track form). The biggest launch gaps are not missing pages but lies and dead ends: the entire monetization layer is decorative (no checkout exists despite the FAQ promising one and a dead Upgrade button), the signup funnel silently drops users onto the sign-in form, most fetch handlers convert server errors into "you have no data" empty states, and the UI never shows scrape freshness even though the whole product depends on a Mac Mini daemon that can silently stall. The ROUTING-OPTIONS.md concern (scraper hook analysis routed through the Anthropic API) is resolved in code — scraper/hooks.py now calls the local OpenClaw endpoint — but that resolution itself couples a customer-facing feature to a personal-subscription gateway on the operator's machine.

### Infrastructure & Ops

The app builds cleanly (npm run build exits 0) and secrets hygiene in git is good (.env.local, terraform state, and tfvars are all gitignored and never appear in git history; no hardcoded API keys or AWS keys in tracked source). However, launch-blocking operational gaps remain: the RDS instance is publicly accessible with port 5432 open to 0.0.0.0/0, has effectively no backup posture (1-day retention, skip_final_snapshot, no deletion protection), the product's core flow depends on an unmonitored Mac Mini daemon with zero alerting or health checks, there is no error monitoring or analytics anywhere in the stack, and the legally required Terms/Privacy pages referenced on the login page do not exist — which also blocks TikTok OAuth app review. Tooling has drifted: `npm run lint` currently fails with 4 errors because eslint-config-next is pinned to 16.1.6 (Next 16/React Compiler rules) against a Next 14/React 18 app, and @types/react is v19 against React 18. next-auth is pinned to a v5 beta. The README still describes a SQLite/mock-auth MVP that no longer exists.

### AI Features

The AI layer gets the basics of key handling right — the DeepSeek key is read from process.env server-side only, nothing is exposed via NEXT_PUBLIC, and no env files or hardcoded keys exist anywhere in git history (verified). Prompt construction is thoughtful (static system messages for DeepSeek prefix caching) and the Python pipeline has good local hygiene (httpx/subprocess timeouts, per-account analysis caps, >5min video skip). But the system is not launch-ready on robustness or cost control: /api/analyze-hook is fully unauthenticated and bypasses every analysis cost cap; the Mac Mini daemon livelocks in a zero-sleep infinite retry loop the first time a queued post fails analysis (a guaranteed occurrence given the top-5 queueing has no duration/video filter), which silently halts ALL scraping; there is zero rate limiting or per-user quota on any of the five DeepSeek endpoints; regenerate persists unvalidated model output and can null out a user's existing playbook section; scraped captions flow unsanitized into prompts whose structured output is trusted, stored in a globally shared patterns table, and re-injected into other users' generation prompts; and the web routes have no fetch timeouts or maxDuration config. The two criticals (unauthenticated compute trigger, daemon livelock) should be fixed before launch; rate limiting and output validation soon after.
